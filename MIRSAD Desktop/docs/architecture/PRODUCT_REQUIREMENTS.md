## 0) الغرض من هذه الوثيقة وكيفية استخدامها

هذه الوثيقة تجمع طلب صاحب المشروع وتصورًا شاملًا لتطوير **MIRSAD Desktop** كتطبيق مستقل عن ArcMap وArcGIS Pro، مع الإبقاء على الـ Toolbox الحالية دون تغيير أثناء بناء البديل. تصلح لأن توضع في جذر المستودع أو داخل `docs/` وتُستخدم كنقطة انطلاق في محادثات ChatGPT/Codex ومهام التطوير المتعاقبة.

**مهم:** لا تعتبر الأسماء البرمجية والأدوات والتصاميم الواردة هنا وصفًا لما هو موجود بالفعل في المستودع؛ إنما هي **اقتراحات** إلى أن يُفحص الكود المصدري والبيانات والشعار والملفات الملحقة. لم تُجرَ في إعداد هذه الوثيقة مراجعة لملفات `.pyt` الفعلية لأنها لم تكن متاحة في سياق العمل.

### قرارات مراجعة 17 أكتوبر 2026

- الواجهة المطلوبة مساحة عمل جغرافية متكاملة: Add Data، وخريطة تفاعلية وخلفيات، ونقاط مستخدم ومحطات وشبكة إقليمية، واختيار CRS وطريقة المعالجة، والوضع الداكن، وتقدم محدد، ودليل داخل التطبيق.
- مجموعات العناصر والنماذج الـ19 جزء من نطاق النقل. سجل مستقل يصرح بتبعيات المصدر؛ لا تُختزل الواجهة إلى الحرارة والأمطار ولا يُعرض مصدر غير منفذ.
- قراءة GIS والتنزيل والمعالجة في عمليات منفصلة عن الواجهة، بعقود JSON محددة وسجلات محلية وحدود للمدخلات؛ انهيار العامل لا يغلق مساحة العمل.
- بيانات المنتج داخل EXE والتوقيع الرقمي مطلبان منفصلان؛ الناشر الموثوق يحتاج شهادة فعلية ولا يعالج بتعطيل حماية Windows.

- اعتماد **Esri File Geodatabase (`.gdb`) كمخرج أساسي مطلوب في MVP**، وإنتاج **GeoPackage (`.gpkg`) بجانبها** افتراضيًا؛ لأن سير عمل المستخدم يعتمد أساسًا على Esri.
- الحد الأدنى المطلوب داخل `.gdb`: Feature Classes حقيقية للمحطات وحدود الدراسة والعناصر المناخية الناتجة. لا تُشترط جداول القياسات اليومية المستقلة أو خصائص Esri المتقدمة في النسخة الأولى؛ تبقى جداول السمات ملازمة لكل Feature Class.
- إبقاء الاستقلال عن ArcGIS و`arcpy` شرطًا أساسيًا. مسار التنفيذ المقترح هو GDAL/OGR مع `OpenFileGDB`، مع إثبات إنشاء البيانات وإعادة قراءتها من الحزمة المستقلة قبل اعتمادها.
- استخدام المجلد الموجود فعليًا **`MIRSAD Desktop/`** داخل المستودع؛ لا إنشاء مشروع موازٍ باسم مختلف.
- فوّض صاحب المشروع بدء التنفيذ بعد هذه المراجعة. الحالة الفعلية والتسليمات الحالية في `docs/CHANGELOG.md`؛ لا يُعتبر اكتمال الشريحة الأولى اكتمال الأطلس كله.
- مكانا التشغيل الثابتان فقط: `runtime/development/MIRSAD.exe` للتطوير و`runtime/stable/MIRSAD.exe` للنسخة المعتمدة. تُستبدل نسخة التطوير بعد الاختبار، وتُنقل الحزمة المراجَعة إلى النهائية بعد موافقة المستخدم فقط؛ لا نسخ تشغيل مرقمة أو مؤرخة.
- كتالوج المحطات مضمن في حزمة البرنامج، مع إصدار وبصمة موحدين مع مصدر الـToolbox؛ لا قراءة لملفات الـToolbox أثناء تشغيل Desktop.

### النص الأصلي لطلب صاحب المشروع (للاحتفاظ بالسياق)

> بقولك بقى إحنا عايزين نعمل شات مع بعض في داخل المشروع دوت. الغرض منه هو إن نحول التول بوكس دي نعمل فولدر بقى جديد جوه الأداة ونسميه مثلاً، يعني بقى يبقى اسم البرنامج باسم مرصاد واللوجو موجودة هو، ويكون البرنامج ده ملوش علاقة بقى بالأرك ماب، ويبقى مستقلة لوحدها، خاص بتحميل البيانات وتأهيل ملفات الإكسل مثلاً، أو لو هو يقدر يcarry database بالـshapefiles بتاعتها وكل حاجة، يبقى مية مية يعني، يعني ينشئ database ويكاريت الـdatabase ويحط فيها، كأن الأدوات بتشتغل في هيكل برنامج مستقل، فاهمني؟ بحيث نتلافى أخطاء الأرك ماب مع الأدوات دي. إيه رأيك بقى؟ وإنت معاك تقدر تقرأ المشروع بالملفات اللي موجودة وتقدر تقترح عليا واجهة الأداة تبقى عاملة إزاي، البرنامج يبقى عامل إزاي وهكذا. يبقى برنامج قابل للتثبيت وإلغاء التثبيت ولها الهوية بتاعتنا موجودة، وطبعاً المطور هتبقى عارف بياناته وما إلى ذلك، وهيبقى مربوط بجيت هاب أو ما إلى ذلك برضه نفس القصة، هيبقى داخل نفس التولز، هيبقى داخل نفس مجلد المشروع.

### الهدف النهائي في عبارة واحدة

بناء **برنامج سطح مكتب مستقل قابل للتثبيت والإزالة** باسم **مرصاد — MIRSAD**، بهوية بصرية وشعار وبيانات مطور، لتنزيل بيانات محطات الطقس، ومعالجة Excel/CSV، وإدارة قواعد البيانات والطبقات الجغرافية، وتشغيل التحليلات وإنتاج أطالس وملفات GIS **من دون اشتراط تثبيت ArcMap أو ArcGIS Pro أو الاعتماد على `arcpy` في محرك البرنامج الجديد**.

## 1) الرؤية وحدود المشروع

### 1.1 الرؤية

تحويل الخبرة والوظائف الموجودة في Toolbox مرصاد إلى منصة Windows موحدة تغطي دورة حياة بيانات الأرصاد: اكتشاف المصادر والمحطات، تنزيل السجلات، التحقق والجودة، تنظيم البيانات، تحويلها إلى طبقات مكانية، إدارة قاعدة بيانات المشروع، التحليل والاستيفاء، العرض، والتصدير والتوثيق.

### 1.2 مبادئ ملزمة

1. **الاستقلال التشغيلي:** وظائف البرنامج الجديدة لا تتطلب رخصة ArcGIS أو تثبيت ArcMap/ArcGIS Pro.
2. **عدم كسر القديم:** الإبقاء على ملفات الـ Toolbox الأصلية كما هي في البداية. لا نقل أو حذف أو إعادة تسمية لها دون تدقيق وموافقة.
3. **الفصل بين المحرك والواجهة:** أي وظيفة معالجة يجب أن تعمل برمجيًا دون GUI، وأن تكون قابلة للاختبار من خلال واجهة CLI أو اختبارات آلية.
4. **التوافق البيني:** مخرجات يمكن فتحها في QGIS وArcGIS Pro عند الحاجة؛ عدم ربط مرصاد بأحدهما.
5. **شفافية النتائج:** توثيق المصادر، فترات الرصد، معايير الاستبعاد، أنظمة الإحداثيات، خطوات التحويل، وتواريخ التشغيل.
6. **حماية البيانات:** لا تمسح إزالة البرنامج ملفات مشروعات المستخدم أو قواعد بياناته دون موافقة صريحة.
7. **التدرج:** البدء بالتنزيل والجداول وقواعد البيانات، ثم نقل التحليلات وإنشاء الأطالس بعد إثبات تكافؤ النتائج.
8. **الوضع دون إنترنت:** إتاحة فتح المشروعات وتحرير البيانات المحلية وتحليلها دون اتصال؛ وظائف التنزيل تتطلب اتصالًا عند الحاجة.

### 1.3 داخل النطاق

- واجهة Windows باسم وشعار مرصاد.
- إدارة المشروعات، والمجلدات، وإعدادات التشغيل.
- تنزيل بيانات محطات الأرصاد من المصادر المعتمدة داخل المشروع القائم بعد فحصها.
- تحديد الدولة أو المنطقة أو ملف حدود الدراسة، وإضافة محطات الهالة المحيطة إن توفرت.
- معالجة Excel وCSV: الاستيراد، التنسيق، القيم المفقودة، التكرار، الوحدات، التواريخ، الإحداثيات، جودة السجلات.
- إنشاء File Geodatabase وGeoPackage معًا، وإضافة طبقات المحطات والعناصر المناخية إلى الصيغتين؛ حفظ جداول القياسات في GeoPackage أو SQLite وExcel حسب التصميم، واستيراد/تصدير Shapefile والملفات المدعومة.
- إنتاج مخرجات Raster/GeoTIFF وأطلس مناخي عندما تُنقل وحدات التحليل وتُختبر.
- معاينة خرائط وطبقات وبيانات وصفية.
- سجلات تشغيل مفصلة، تقدم التنفيذ، وقف آمن، واستئناف/إعادة محاولة العمليات القابلة لذلك.
- حزمة تثبيت وإزالة وتحديد رقم الإصدار وهوية المطور، ومستودع GitHub مشترك.

### 1.4 خارج النطاق في الإصدار الأول

- بناء بديل كامل لجميع إمكانات ArcGIS Desktop.
- ادعاء دعم كل وظائف Esri Geodatabase المتقدمة دون اختبارات توافق.
- خوادم سحابية، أو حسابات متعددة المستخدمين، أو مشاركة آنية، ما لم تصبح مطلبًا مستقلًا.
- تحويل جميع أدوات Toolbox إلى وظائف مكتملة دفعة واحدة.
- تحديث ملفات مصدرية أو نشر إصدار GitHub دون مراجعة التغييرات والموافقات اللازمة.

## 3) الوظائف المطلوبة بالتفصيل

### 3.1 لوحة التحكم والمشروعات

- إنشاء مشروع جديد باسم ومسار وملف إعدادات.
- فتح مشروع قائم أو مشروع حديث الاستخدام.
- تحديد الدولة والنطاق المكاني والفترة الزمنية ووحدات القياس ونظام الإحداثيات المستهدف.
- مؤشرات لحالة المشروع: عدد المحطات، السجلات، الملفات، التنزيلات، الطبقات، المهام غير المكتملة.
- استعراض `Input / Database / Outputs / Logs` دون تغيير مواقع المستخدم من تلقاء البرنامج.
- قوالب مشروعات قابلة لإعادة الاستخدام مثل «الأطلس المناخي لمصر».

### 3.2 تنزيل بيانات المحطات المناخية

ينبغي أن تنعكس إعدادات الـ Toolbox المعروفة من سجل الاستخدام السابق، مع مراجعة الكود لتحديد ما يعمل منها فعليًا:

- **Station Selection Mode:** الاختيار حسب الدولة/الشبكة الوطنية، أو معرفات محطات، أو طبقة نقاط محلية.
- **Region Filter:** مثل الدول العربية عند توفر مرجع موثوق للدول.
- **Country / Scope:** مثال مصر (EG).
- **Study Area Boundary:** حدود اختيارية لاختيار/قص نطاق الدراسة.
- **Supplementary Survey Points:** نقاط إضافية مع تمييزها عن محطات الرصد الحقيقية.
- **Neighboring Buffer Stations:** خيار تضمين محطات في نطاق 30 كم (قيمة قابلة للتعديل) حول حدود الدراسة، مع توثيق طريقة حساب المسافة.
- **Custom Station IDs:** مدخل معرفات محطات مثل USAF عند دعم المصدر.
- **Local Station Layer:** طبقة نقاط محلية للدمج/الاستيراد.
- **Operation Mode:** تنزيل فقط / تنزيل ثم إنشاء قاعدة بيانات / خط معالجة كامل.
- **Execution Workflow:** تشغيل متسلسل أو متوازٍ بحذر وفق قيود المصدر.
- **Output Workspace + CRS:** مسار واضح وCRS معروف وصحيح.

**المطلوب وظيفيًا:** عرض المصدر، إجمالي المحطات المرشحة، نسبة التحميل، السجلات المكتملة، فشل المحطات وأسبابه، إعادة المحاولة، القدرة على استئناف التنزيل الجزئي، ومنع تكرار السجلات في قاعدة البيانات.

**الاعتمادية:** إضافة مهلات اتصال، Backoff، عدد محاولات محدود، Rate Limiting، تحقق من المحتوى، واحترام شروط استخدام مصادر البيانات. عدم تسجيل كلمات المرور أو رموز API في ملفات السجل.

### 3.3 تجهيز ملفات Excel وCSV

- اختيار ملفات فردية أو مجلدات وإظهار معاينة أولية للصفوف والأعمدة.
- التعرف على Encoding والفواصل وتواريخ وتوقيتات السجلات بصورة صريحة وقابلة لتعديل المستخدم.
- توحيد أسماء الأعمدة وفق Schema مع حفظ عمود المصدر الأصلي عند الحاجة.
- ربط معرف المحطة والاسم وخط الطول والعرض والارتفاع والمتغير والفترة ووحدة القياس.
- اكتشاف Duplicate keys، Nulls، التواريخ غير الصحيحة، الإحداثيات خارج المدى، القيم المتطرفة، والوحدات المختلطة.
- عدم حذف السجلات المشكوك فيها بصمت؛ إنتاج Quality Flags وتقرير تنظيف.
- الإخراج الأساسي للجداول إلى XLSX مع Metadata وManifest؛ دعم استيراد CSV، واستخدامه في التصدير عند اختياره صراحة أو كبديل معلن عند تعذر Excel. إتاحة الملف المجمع وملفات كل سنة على حدة وفق إعداد المستخدم.
- الاحتفاظ بالملفات الخام دون تغيير في `data/raw` قدر الإمكان.

### 3.4 محرك قواعد البيانات والطبقات

**قرار المنتج:** **Esri File Geodatabase (`.gdb`) وOGC GeoPackage (`.gpkg`) مخرجان أساسيان متوازيان**، ويُفعّل إخراجهما معًا افتراضيًا. المقصود File Geodatabase المحلية، وليس قاعدة Enterprise/SDE أو Personal Geodatabase (`.mdb`). يمكن استخدام GeoPackage/SQLite داخليًا لإدارة المشروع، لكن هذا اختيار تنفيذي لا يُلغي تسليم `.gdb` للمستخدم.

تُكتب طبقات المحطات وحدود الدراسة والعناصر المناخية كـ **Feature Classes أصلية داخل `.gdb`**، وبنفس الحقول المناخية والمعرّفات والهندسة ونظام الإحداثيات داخل `.gpkg`. عند استيراد Shapefile تتحول بياناتها إلى Feature Class؛ لا يكفي نسخ ملفات `.shp` و`.dbf` إلى مجلد اسمه `.gdb`. توضّح [وثائق Esri لاستيراد البيانات](https://doc.esri.com/en/arcgis-pro/latest/help/data/geodatabases/overview/import-data.html) الفرق بين الاستيراد وصيغة الطبقة الناتجة.

**جداول القياسات اليومية المستقلة ليست شرط قبول داخل `.gdb`**. يمكن الاحتفاظ بها في GeoPackage أو SQLite وملفات Excel. أما جداول السمات والحقول المناخية داخل Feature Classes فهي جزء أساسي من المطلوب. تُحفظ GeoTIFF منفصلة، مع مراجع إليها في Manifest، ولا يُشترط تخزين Raster داخل `.gdb` في MVP.

عمليات الواجهة:

- Create Databases: إنشاء `<project>.gdb` و`<project>.gpkg` باسم المشروع، مع خيار واضح لاحقًا لإخراج صيغة واحدة فقط إذا اختار المستخدم ذلك صراحة.
- Import Shapefile: قراءة مكوناتها والتحقق من CRS والحقول والتكويد، ثم كتابة بياناتها كطبقات/Feature Classes داخل الصيغتين؛ لا تخزين ملفات Shapefile نفسها داخل قاعدة البيانات.
- Import CSV/Excel: حفظ جدول أو إنشاء طبقة نقاط بعد تعيين الإحداثيات.
- Add Boundary / Stations / Observations / Analysis Layers.
- Validate: هندسات غير صالحة، CRS مفقود، سمات مطلوبة، تكرار المحطات، سلامة قاعدة البيانات.
- Reproject / Export: File Geodatabase وGeoPackage كمخرجين مطلوبين، وShapefile وGeoJSON وGeoTIFF وExcel حسب العملية؛ CSV عند اختياره أو كبديل معلن.
- إنشاء نسخ احتياطية للبيانات قبل العمليات عالية المخاطرة، وعدم الكتابة فوق ملف من دون اختيار واضح.

### 3.4.1 مسار File Geodatabase المستقل

توثق [GDAL: OpenFileGDB](https://gdal.org/en/stable/drivers/vector/openfilegdb.html) دعم الإنشاء والتحديث منذ GDAL 3.6، وأن الدرايفر لا يعتمد على مكتبة خارجية من Esri. هذه قدرة تقنية مناسبة للمطلوب، وليست إثباتًا بأن حزمة مرصاد قد نفذتها. يُختار إصدار مستقر محدد وتُحزم تبعياته مع التطبيق؛ وجود GDAL على جهاز المطور لا يكفي لقبول إصدار التوزيع.

- إنشاء قاعدة جديدة وطبقات Point/LineString/Polygon بحسب نوع كل ناتج، مع اختبار Multipart عند وجوده في حدود الدراسة.
- حفظ الحقول العددية والعربية وNULL ومعرّفات المحطات النصية التي قد تبدأ بصفر؛ لا تُستخدم أرقام OBJECTID المولّدة للربط بين الصيغتين.
- الكتابة مباشرة من Schema النتائج إلى FileGDB، دون المرور الإجباري بـShapefile وسيطة. تُحفظ أسماء الحقول الأصلية المتوافقة مع Esri، وتُختبر Aliases العربية عند اعتمادها.
- تعريف ملف توافق افتراضي للحقول والهندسة يستهدف ArcMap 10.8 وArcGIS Pro، واختباره فعليًا في البرنامجين. عند استخدام GDAL يدعم `TARGET_ARCGIS_VERSION=ALL` يُختبر هذا الإعداد، مع حصر أي تحويل لأنواع الحقول في تقرير التوافق؛ لا يُفترض تطابق كل أنواع الحقول بين الإصدارات.
- لا تشمل متطلبات MVP: Topology أو Utility Network أو Versioning أو قواعد السمات والعلاقات والمرفقات المتقدمة. يضاف أي مطلب منها لاحقًا بعد اختبار مستقل.
- أي دعم إضافي يعتمد على ArcGIS يُفصل في موصل اختياري مستقبلًا؛ لا يكون مسارًا خفيًا أو شرطًا لإنشاء الطبقات الأساسية المطلوبة.

### 3.4.2 اتساق المخرجين والفشل الجزئي

- تُحسب النتائج مرة واحدة، ثم يغذي نفس Schema و`run_id` ومعرّفات السجلات كاتب GeoPackage وكاتب FileGDB. تُحفظ جداول المشروع الداخلية في مخزن واحد؛ لا تُبنى مزامنة تحرير ثنائية الاتجاه بين قاعدتين في MVP.
- يُسجَّل في Manifest لكل طبقة: الأعداد، أسماء الحقول وأنواعها، CRS، امتداد البيانات، مواقع المخرجات، والتحويلات أو الفروق المقبولة. تُحدد حدود دقة عددية وهندسية معلنة للمقارنة، لأن التخزين قد يغيّر تمثيل الكسور أو دقة الإحداثيات.
- فشل `.gdb` لا يتحول بصمت إلى نجاح كامل لمجرد نجاح `.gpkg`: تعرض المهمة «نجاح جزئي» وتحدد سبب الفشل، وتحفظ المخرج السليم، وتتيح إعادة محاولة التصدير دون إعادة التنزيل أو الحساب.
- لا يُقبل الإصدار المستقل إذا كان إنشاء `.gdb` المطلوب غير متاح في الحزمة؛ يبقى إصدارًا تجريبيًا حتى يُحل السبب. Shapefile مستقل خيار إضافي، وليس بديلًا يحقق شرط File Geodatabase.

### 3.5 التحليل والأطالس — مراحل تالية

- تجهيز السلاسل الزمنية وتلخيص المؤشرات المناخية التي تثبت مراجعة Toolbox أنها جزء من المشروع.
- حساب الإحصاءات والتغيرات الزمنية والملخصات المكانية.
- Interpolation بإعدادات معلنة: اختيار الطريقة والمعلمات وتحقق Cross-Validation والمقارنة.
- قص Raster بحدود الدراسة، NoData، Resampling، وحدات، وإدارة CRS.
- تصدير GeoTIFF وجداول نتائج وتقارير وإخراج خرائط/أطلس PDF حين تُحدد وظائفه القائمـة بشكل دقيق.
- مقارنة نتائج المحرك الجديد بملفات مرجعية من الـ Toolbox لتجنب اختلافات علمية غير مفسرة.

## 5) المعمارية البرمجية المقترحة

```text
Presentation Layer (PySide6 / Qt)
           |
Application Services / Use Cases
           |
Domain Models + Validation + Task Orchestrator
           |
+------------------+-------------------+-------------------+
| Download Adapters| Tabular Processing| Spatial Processing|
| HTTP / Sources   | Pandas / OpenPyXL | GDAL / GeoPandas  |
+------------------+-------------------+-------------------+
           |
Project Store (GeoPackage / SQLite) + files + manifests
           |
Export Adapters (OpenFileGDB .gdb + GeoPackage .gpkg + Excel)
           |
Logs + Provenance + Exports + Optional CLI
```

**توصيات تقنية أولية غير ملزمة إلى ما بعد فحص الإصدارات والكود:**

| المجال | اختيار مبدئي | ملاحظات |
|---|---|---|
| Desktop UI | PySide6 | GUI أصلي لـ Windows وRTL؛ التحقق من متطلبات LGPL/GPL/Commercial عند التوزيع |
| Download | requests/httpx | Backend قابل للاختبار واحترام Rate Limits |
| Excel/CSV | pandas + openpyxl | مع قواعد تحقق صريحة وتوثيق Quality Flags |
| Vector GIS | GDAL/OGR + GeoPandas + Shapely + PyProj | أولوية GDAL للاستيراد/التصدير المعقد وCRS |
| Storage | SQLite + GeoPackage داخليًا؛ مخرجات GeoPackage + Esri FileGDB | كاتبان من Schema موحد؛ OpenFileGDB للـ .gdb، وفهارس وسجلات عمليات وMetadata |
| Raster/Analysis | Rasterio + NumPy + SciPy | لا تعتمد المعالجة على `arcpy` |
| Jobs | QThreadPool / Qt Signals أو workers | عدم تجميد GUI؛ تصميم قابل للإلغاء والتوقف الآمن |
| Logging | Python logging + structured context | log per run؛ فصل مستوى رسالة المستخدم عن Stack Trace |
| Tests | pytest | Unit / Integration / Regression / End-to-end |
| App Packaging | pyside6-deploy / Nuitka / PyInstaller (بعد تجارب) | اختيار أحدها بناءً على GDAL/Qt وملحقات Windows |
| Windows Installer | Inno Setup أو WiX | تثبيت / ترقية / إزالة نظيفة |
| Automation | GitHub Actions Windows runner | Build + tests + signed/release artifacts عند توفر الشهادات |

### 5.1 منع تسرب الاعتماد على ArcGIS

- `app/core`, `app/spatial`, `app/downloaders`, `app/database` يجب ألا تستورد `arcpy` إطلاقًا.
- يمكن الاحتفاظ بـ `legacy/` أو ملفات Toolbox القديمة مستقلة، دون إدراجها في إصدار MIRSAD Desktop.
- ملفات GDB والـ Shapefile هي **صيغ بيانات متوافقة**، وليست سببًا للاعتماد على ArcGIS.
- أي وظيفة غير قابلة للنقل يصرّح بها في تقرير التدقيق؛ لا تُعتبر منفذة لمجرد وجود زر باسمها.
- تُختبر حزمة GDAL مستقلة ببيئة معزولة؛ يُمنع الاعتماد على Python أو DLLs أو PROJ/GDAL data المأخوذة من تثبيت ArcGIS لدى المستخدم. يجب أن يحمل Installer التبعيات التي يحتاجها التطبيق.

### 5.2 تصور نموذج البيانات

الحد الأدنى المقترح للجداول/الكيانات:

| Entity | أهم الحقول والاعتبارات |
|---|---|
| `stations` | `station_id` فريد، `source`, `name`, `latitude`, `longitude`, `elevation_m`, `geometry`, `crs`, `metadata` |
| `observations` | `station_id`, `observed_at_utc`, `variable_code`, `value`, `unit`, `quality_flag`, `source_record_id`؛ مفتاح منطقي لمنع التكرار |
| `source_catalog` | `source_id`, اسم المصدر، URL/endpoint، الترخيص، last_checked، النسخة |
| `download_runs` | `run_id`, المدى الزمني، المرشحات، البداية والنهاية، الحالة، عدد المحطات، الأخطاء |
| `data_quality_issues` | نوع المشكلة، record/table reference، severity، resolution |
| `processing_runs` | المدخلات، إعدادات الخوارزمية، نسخة المحرك، بصمات ملفات، المخرجات |
| `project_layers` | اسم الطبقة، نوعها، CRS، الموقع، source/provenance، date_created |
| `project_assets` | مسارات ملفات Excel/CSV/GeoTIFF الخارجية، Hash، حجم، نوع |

> لا يُفترض أن كل هذه الجداول ينبغي تخزينها في GeoPackage واحد. يعتمد التقسيم النهائي على أحجام السلاسل الزمنية واحتياجات الاستعلام والتوافق. قد تكون قاعدة SQLite منفصلة للمهام/الإعدادات مناسبة، مع GeoPackage للبيانات المكانية.

**انعكاس النموذج على `.gdb`:** يُصدَّر الجزء المكاني المطلوب للمستخدم: المحطات، الحدود، وFeature Class لكل عنصر مناخي ناتج مع سماته. لا يلزم نسخ جداول المهام والإعدادات والسلاسل اليومية الداخلية إلى `.gdb` في MVP. بيانات التعريف الأساسية تبقى قابلة للتتبع عبر Manifest ومعرّفات ثابتة.

### 5.3 عقود البيانات والأخطاء

- اعتماد UTC داخليًا مع الاحتفاظ بالتوقيت الأصلي والمصدر والمنطقة الزمنية إن وجدت.
- تخزين البيانات الخام وفصلها عن القيم المعالجة.
- الفصل بين Missing وRejected وImputed وFlagged.
- تسجيل EPSG أو تعريف CRS صالح، وتجنب إعادة إسقاط غير صحيحة.
- كل عملية تُرجع `status`, `metrics`, `warnings`, `errors`, `output_paths` بصورة منظمة.
- العمليات الكبيرة تُنفذ في Workers، وتعرض نسبة إن كانت قابلة للحساب؛ بخلاف ذلك تُعرض مرحلة التنفيذ.

## 7) النسخة الأولى MVP ومعايير القبول

لا تنتقل إلى مرحلة الأطالس قبل اجتياز الاختبارات الأساسية.

### 7.1 متطلبات MVP

- [ ] تشغيل MIRSAD Desktop على جهاز Windows نظيف **بلا ArcMap أو ArcGIS Pro أو arcpy**.
- [ ] نافذة تحمل هوية مرصاد وشعاره المعتمد وبيانات إصدار حقيقية.
- [ ] إنشاء مشروع وحفظ/فتح مشروع موجود.
- [ ] تنزيل بيانات من مصدر واحد على الأقل يستخدمه المشروع القديم فعلًا، مع إظهار ما نجح وما فشل.
- [ ] اختيار مصر ونطاق دراسة اختياري ونظام إحداثيات للمخرجات.
- [ ] استيراد ملف CSV وExcel، مع معاينة وتعيين الحقول وتقرير جودة.
- [ ] إنشاء GeoPackage صالح وإضافة طبقة محطات وجداول بيانات.
- [ ] إنشاء File Geodatabase حقيقية بجانب GeoPackage، تحتوي Feature Classes للمحطات وحدود الدراسة عند توفيرها ولكل عنصر مناخي محسوب في MVP؛ لا تُشترط جداول يومية مستقلة داخلها.
- [ ] مطابقة أعداد المعالم والمعرّفات والسمات وCRS بين المخرجين ضمن التحويلات الموثقة؛ فتح وإعادة قراءة المخرجين بعد إغلاق الكاتب.
- [ ] تنفيذ إنشاء وقراءة وتحديث عينة FileGDB من الحزمة الموزعة على Windows نظيف بلا ArcGIS، مع فحص توافق ناتجها في ArcMap 10.8 وArcGIS Pro على أجهزة التحقق المنفصلة.
- [ ] عرض النجاح الجزئي وإتاحة إعادة تصدير `.gdb` من النتائج المحفوظة دون إعادة التنزيل عند فشل أحد الكاتبين.
- [ ] استيراد Shapefile متعدد الملفات إلى طبقة قابلة للقراءة مع فحص CRS والهندسة.
- [ ] تصدير طبقة إلى Shapefile/GeoPackage أو CSV مع التحقق من النتيجة.
- [ ] عدم توقف الواجهة خلال عمليات تنزيل/استيراد كبيرة.
- [ ] رسائل أخطاء مفهومة وسجلات تقنية كاملة للمراجعة.
- [ ] Setup + Uninstaller مع الحفاظ على مشروعات المستخدم.
- [ ] اختبارات Python آلية وملف تعليمات تثبيت وتطوير.

### 7.2 حالات اختبار مهمة

- ملف Excel بترميز مختلط وأعمدة عربية وإنجليزية.
- محطة بها إحداثيات ناقصة أو خارج النطاق.
- سجلات مكررة أو قياسات ذات وحدات مختلفة.
- انقطاع الاتصال أثناء تنزيل 100 محطة، ثم استئناف/إعادة محاولة الفاشل.
- حدود مصر ومناطق بحرية/جزر والتقاطع مع Buffer؛ التحقق من حساب المسافات في CRS ملائم.
- مسارات Windows تشمل أحرفًا عربية وفراغات.
- مجلد Output للقراءة فقط أو مساحة تخزين غير كافية.
- ملف GeoPackage قيد الاستخدام أو Layer CRS غير معروف.
- قاعدة `.gdb` قيد الاستخدام، أو فشل الكاتب بعد نجاح `.gpkg`، أو غياب دعم OpenFileGDB من الحزمة؛ لا نجاح كامل مضلل.
- Feature Classes بنص عربي، ومعرّف يبدأ بصفر، وNULL وقيم عشرية، وحدود Multipart؛ مقارنة إعادة القراءة في المخرجين واختبار اختيار/تحديد المعالم في ArcGIS.
- تثبيت وترقية وإزالة التطبيق ثم التأكد من بقاء مشروعات المستخدم.

### 7.3 معايير قبول التحليل المناخي لاحقًا

- اختيار Dataset مرجعي من التشغيل القديم.
- تثبيت معلمات الاستيفاء والـ CRS وNoData وحدود القص.
- مقارنة الإحصاءات والطبقات والراستر وتوثيق فروق المعالجة العددية المقبولة علميًا.
- لا تُعلن وظيفة «مكتملة» قبل مرورها باختبارات فعلية، ولا تنقل `arcpy` إلى المحرك الجديد كحل سريع.

## 8) خطة التنفيذ المرحلية

### المرحلة 0 — Discovery & Architecture

**العمل:** جرد المستودع والكود والموارد، وفحص `arcpy`، وتحديد وحدات قابلة للنقل، وحصر مصادر البيانات وشروطها، ورسم حدود MVP.

**التسليمات:** تقرير تدقيق؛ مصفوفة نقل؛ معمارية نهائية أولية؛ قائمة مخاطر؛ لقطة مقارنة بالمخرجات القديمة.

**بوابة تقنية مبكرة:** قبل توسيع الواجهة، إثبات مسار صغير: عينة محطات وحقول مناخية → GeoPackage + FileGDB → إغلاق وإعادة فتح ومقارنة. يُختبر نموذج حزمة Windows مستقلة مبكرًا؛ لا يُؤجل اكتشاف مشاكل GDAL/PROJ/Qt إلى نهاية المشروع. الفحص المحلي لهذه المراجعة وجد OpenFileGDB في GDAL المرفق بـArcGIS Pro، ولم يجد GDAL في Python العام المتاح للمحادثة؛ هذا جرد محلي فقط ولا يثبت الاستقلال التشغيلي.

### المرحلة 1 — Core Desktop MVP

**العمل:** إنشاء تطبيق PySide6 مستقل، Config ومشروعات، Downloaders، Excel/CSV Processing، Database Services، Import/Export، Logging، Tests.

**التسليمات:** تشغيل البرنامج في بيئة تطوير وعينة ناجحة من مسار: تنزيل مصدر منفذ → تنظيف وحساب الحقول الداخلة في MVP → GeoPackage + FileGDB → Excel؛ ثم تحقق من المخرجين دون إعادة الحساب.

### المرحلة 2 — GIS Visualization & Workflows

**العمل:** خريطة مصغرة وشجرة طبقات وجدول سمات، CRS وBounds وBuffer، مهام خلفية وسجل تنفيذي متقدم.

**التسليمات:** تطبيق قابل للاستخدام اليومي للبيانات الجغرافية دون ArcGIS.

### المرحلة 3 — Climate Atlas & Analysis

**العمل:** نقل العمليات المناخية المؤكدة من Toolbox إلى محرك مستقل؛ الاستيفاء/الراستر/الأطلس؛ Regression tests.

**التسليمات:** مطابقة علمية موثقة، وأطلس مناخي مستخرج من MIRSAD Desktop.

### المرحلة 4 — Windows Distribution & GitHub Releases

**العمل:** Packaging موثوق لـ Qt/GDAL، Installer، Uninstaller، أيقونات، إصدار، اختبارات Windows، إصدار GitHub.

**التسليمات:** `MIRSAD_Setup.exe` وملف Release Notes وChecksum وتوثيق المستخدم؛ Code Signing عند توفر شهادة مناسبة.

## 11) ترتيب الأولويات واتخاذ القرارات

**قرارات مقترحة يمكن البدء بها:**

- Windows 64-bit أولًا.
- PySide6 للواجهة.
- GeoPackage/SQLite كمخزن داخلي عملي، مع إخراج GeoPackage وEsri File Geodatabase معًا افتراضيًا؛ FileGDB للطبقات الأساسية شرط MVP.

- تحميل + تجهيز جداول + إنشاء قاعدة GIS أولًا؛ الأطالس لاحقًا.

**قرارات يجب تأكيدها من مستودع المشروع لا من التخمين:**

- تفاصيل لوجو مرصاد وبيانات صاحب الحق/المطور.
- أصغر نسخة Windows مدعومة، والتوزيع التجاري من عدمه.

- هل رسم الخرائط والأطلس الحاليان يعتمدان على Layout أو Symbology خاص بـ ArcGIS؟

## 12) تعليمات تنفيذ موجهة إلى Codex / مساعد برمجي داخل المستودع

### المهمة الرئيسية

> أنت تعمل داخل مستودع MIRSAD الموجود بالفعل. الهدف تطوير **MIRSAD Desktop** كبرنامج Windows مستقل يحمل هوية «مرصاد» ويعيد استخدام المنطق القابل للنقل من الـ Toolbox الحالية، دون تبعية تشغيلية لـ ArcGIS/ArcMap/ArcGIS Pro/`arcpy` في التطبيق الجديد. احترم بنية المشروع الحالية ولا تعدّل الملفات الأصلية مبدئيًا. اقرأ هذه الوثيقة كاملة ثم افحص المستودع فعليًا، وحدّث مصفوفة تدقيق قائمة على الملفات الموجودة لا على افتراضات.

### بروتوكول العمل المطلوب

1. **افحص أولًا** شجرة الملفات وGit status والأكواد والموارد والشعار والتبعيات والـ Toolbox. دوّن مسارات الملفات الحقيقية وما نجحت في قراءته. لا تقل إنك قرأت ملفًا لم تقرأه.
2. **ارسم خريطة التبعيات** لكل أداة واكتشف مواضع `arcpy` وعمليات تحميل البيانات وتنظيف Excel/CSV وإنشاء الطبقات وRasters.
3. **اكتب تقرير فجوات** يحدد: Reuse / Refactor / Rewrite، ومخاطر جودة البيانات، ومصادر الحقيقة لعمليات التحليل.
4. **اعرض UI Architecture وDatabase Schema** محدثين بناءً على الكود والبيانات والشعار الفعلي.
5. **استخدم المجلد الموجود** `MIRSAD Desktop/` بعد تحديد جذر المستودع ومنع التداخل مع الملفات الحالية. لا تُعدّل الـ Toolbox إلا بعد تفويض صريح.
6. **نفذ MVP تدريجيًا** عند تفويض التنفيذ، وأول شريحة: تحميل صغير/استيراد جدول → فحص الجودة وحساب الحقول المطلوبة → GeoPackage + FileGDB حقيقية → Excel؛ مع نموذج حزمة مستقل مبكر.
7. **اكتب اختبارات** لكل خدمة وما يقابلها من حالات خطأ، وتأكد من إمكانية تشغيل Core دون `arcpy`.
8. **احتفظ بسجل قرارات** داخل `docs/`، وحدث ملفات README عند كل مرحلة، وأظهر للمستخدم الملفات التي غيّرتها والاختبارات التي نفذتها ونتائجها.
9. **صمم واجهة واضحة** عربية/إنجليزية مع شعار مرصاد المعتمد وبيانات المطور الحقيقية من المشروع، دون وضع أسماء أو شعارات بديلة مختلقة.
10. **بعد استقرار MVP**، نفذ حزمة Windows وتشغيلًا على بيئة نظيفة وراجع ترخيص جميع المكونات قبل التوزيع.
11. **لا تُعلن النجاح** بناءً على إمكانية استيراد الحزم فحسب؛ يجب إثبات تشغيل العينات، سلامة CRS، صحة قاعدة البيانات، وتكافؤ المخرجات عند نقل التحليل.
12. **أوقف العمليات الخطرة** عند احتمال حذف بيانات أو فقد تغييرات؛ اطلب اختيار صاحب المشروع للمسار أو النسخة الاحتياطية قبل الاستبدال.

## 14) ملخص قرار البدء

**الاختيار الموصى به:** نبني **منصة مرصاد** بواجهة ومحرك مستقلين، ومخرجات **Esri File Geodatabase + GeoPackage**، مع Excel كإخراج الجداول الأساسي. FileGDB المطلوبة تضم طبقات العناصر المناخية وسماتها، دون اشتراط الخصائص المتقدمة أو الجداول اليومية المستقلة. نحتفظ بالـ Toolbox الحالية للمقارنة والتحقق، ثم ننقل الأدوات تدريجيًا.

**البداية الصحيحة:** تدقيق الوظائف والتبعيات → إثبات إنشاء وقراءة المخرجين في حزمة مستقلة صغيرة → وثائق تدقيق ومصفوفة نقل → MVP للتنزيل والحقول الأساسية والجداول والقاعدتين → اختبار Windows من دون ArcGIS واختبار توافق المخرجات في Esri → تثبيت وإلغاء تثبيت → استكمال التحليلات والأطلس.

**وضع التنفيذ عند الإنشاء الأصلي:** كانت الوثيقة تخطيطًا فقط. **تحديث 0.3:** بدأ تنفيذ أول شريحة مستقلة تشمل كتالوجًا مضمنًا، واجهة محطات وتنزيل حرارة/أمطار، ومخرجات FileGDB/GeoPackage/Excel؛ تُسجل أدلة الاختبار والبناء وحدود النسخة في خطة التنفيذ. الأطالس والاستيفاء وبقية العناصر والتثبيت والإزالة مراحل لم تُعلن مكتملة.
