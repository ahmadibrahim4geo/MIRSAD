# المرحلة التالية: Excel الكبير في أدوات النقاط والمحطات القديمة

21 أكتوبر 2026. تكمل هذه الدفعة [قبول Desktop](DESKTOP_SOURCE_ACCEPTANCE.md).
ليست تنفيذًا لبقية خيارات الرطوبة/PM/DEM داخل Toolbox أو للمسار الإقليمي.

## السلوك المحدد

`_build_daily_table` يجهز الصفوف في RowSpool يعيد القراءة ويمتد إلى القرص بعد 1 MiB،
بدل جمع نسخة أخرى لكل النقاط في قائمة RAM. تظل قاموس الاستجابات الخام في الذاكرة؛
لا يُدّعى حتى الآن قبول ألف نقطة وثلاثين سنة للمسار الكامل.

في المصدّر الذي تشترك فيه أداة النقاط وأداة المحطات، **إذا تجاوز جدول Daily عدد
60,000 صف** ينتقل المسار من XLS القديم إلى XLSX تدريجي. الطلب الصريح لمسار `.xlsx`
يستخدم الكاتب نفسه مهما كان العدد. يبقى اسم العنصر والمجلد؛ الامتداد الجديد يعلن
في سجل التشغيل. ملفات XLS الصغيرة والتصدير القديم دون هذه الميزة لم يُعاد تعريفهما.
لذلك يبقى CSV fallback القديم في نطاقه السابق فقط، ولا يستخدمه مسار XLSX الجديد
حتى إذا فشل الإنشاء أو كان الملف موجودًا.

كاتب `mirsad_core/xlsx_stream.py` يستخدم مكتبات Python القياسية فقط: لا يلزم تثبيت
openpyxl في Python 2.7 الخاص بـArcMap. الصفوف حرفية؛ لا تنفّذ صيغ من نص غير موثوق.
يحفظ معرفات النص وأصفارها والعربية وNULL والصفر، وRTL والأبعاد وتجميد الرأس. بيانات
Daily القديمة تظل بالتقريب المعتمد في منشئها؛ لا يغير الكاتب حساب المناخ.

مليون صف بيانات لكل ورقة (الرأس إضافي)، وأربعة ملايين لكل ملف. تظهر Daily_2
وPart_002 وExport_Index عند الحاجة، وتتكرر البيانات الوصفية في الأجزاء. تبقى الملفات
المكتملة عند فشل جزء لاحق، ويبلغ السجل عن الفشل والأجزاء؛ لا يستبدل ملفًا قائمًا.
هذا لا يثبت اكتمال إخطار partial-export على مستوى كل تقارير Toolbox القديمة.

## أدلة القبول

- **20 مجموعة معزولة / 168 اختبارًا** نجحت بعد الدمج، ومنها اختبارات XLS الصغيرة
  القديمة والتصدير السنوي وفشل الكاتب ورفض الاستبدال دون CSV في المسار الجديد.
- **9 مجموعات Python 2.7 / 81 اختبارًا** نجحت، تشمل الكاتب دون حزم خارجية.
- خمسة اختبارات مستقلة للكاتب تشمل النص العربي/المعرف والصفر وNULL، ثلاثة ملفات
  بحدود مصغرة وفهرس متسق، حفظ الأجزاء الناجحة، والقراءة بواسطة XML وopenpyxl عند
  Python 3. لا تعتمد اختبارات Python 2.7 على وجود openpyxl. الاختبار الخامس يحمي
  كتابة تقرير الفشل ASCII/Arabic على Python 2.7 و3.
- Python **2.7.18.4، 32 bit** كتب وقرأ **1,000,001 صف** في ورقتين بالحد الافتراضي،
  دون فقد أو تكرار، في **22.028 ثانية** على جهاز التطوير. القراءة والتحضير تدريجيان.
- **ArcGIS Pro 3.6 الأصلي** قرأ Feature Class حقيقية بالمصدّر القديم، وكتب 60,001
  صف إلى XLSX، ثم ExcelToTable إلى FileGDB. نجحت الهوية `001234` وترتيب الأرقام
  والقيم، وحفظ سمات المصدر العربية وهندسته قبل/بعد. هامش إنشاء إحداثيات fixture
  هو 1e-8 درجة؛ الفحص المباشر قبل/بعد يشترط عدم التغيير.
- أعيدت قراءة معاملات المساعدة من Pro: **69/76/36** دون تغيير عدد المعاملات.
  تحديث `tool_parameters.json` يسجل بصمة الكود الحالي؛ ليس معالجة مناخ أصلية.
- baseline الحسابات/الحقول القديمة ما زال ناجحًا. انتقال Daily الكبير إلى XLSX هو
  تغيير إخراج صريح لهذه الدفعة، ولا يُستنتج من baseline أنه لم يتغير أي امتداد جديد.

## ArcMap وحدود التحقق

استيراد ArcPy في البيئة الموجودة أظهر Desktop 10.9.1 وترخيص ArcInfo، رغم اسم مسار
Python الذي يحتوي ArcGIS10.8. الاختباران الأولان لم يتقدما في تهيئة geoprocessor؛
اختبار offline توقف عند `arcpy.Exists`، وأوقفت عمليتي QA الخاصتين بعد 193/205 ثانية.
لم يوقف ذلك برنامج ArcMap أو Pro للمستخدم ولم يغير تثبيتهما. المحاولة المحدودة
تسجل نتيجتها في `tests/.output/native-xlsx-arcmap-bounded/acceptance.json`؛ نجاح
Python 2.7 والكاتب القياسي لا يُحوّل إلى ادعاء قبول معالجة ArcMap الأصلية.

لا تغيير في الخيارات العلمية القديمة أو السجلات الأصلية أو XML الخاصة بالمستخدم،
ولا استبدال للـEXE الحالي. المرشح والمثبت الموثقان في دفعة Desktop لا يتضمنان هذا
الكاتب الخاص بـToolbox؛ Desktop يستخدم كاتبه المستقل الذي اجتاز اختبارات مليون صف.
